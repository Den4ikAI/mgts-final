# ML: Gemini Decision через OpenRouter

Модель `google/gemini-decision-1` отвечает на структурированные вопросы о фото: есть ли объект, какой он, какой дефект (выбор из классов), насколько опасно (шкала). На каждый ответ даёт вероятность. Цена около $0.00016 за фото, ответ около 1.5 с.

| Файл | Что делает |
|---|---|
| `taxonomy.json` | классы, их русские названия и алиасы меток, вопросы, пороги. **Утром правится только он** |
| `decision.py` | клиент API (повторы, кэш по sha256 фото) и правило маршрута |
| `worker.py` | прогон папки → `runs/<id>/predictions.jsonl` и Kafka `detections.created` |
| `evaluate.py` | отчёт против разметки → `runs/<id>/report.{json,md}`, страница «Качество» в UI |
| `labels.py` | чтение CSV/XLSX; `python labels.py table.xlsx` показывает колонки и значения |
| `prepare_dss.py` | сводит 6 таблиц «Датасет-ДСС» в один `labels.csv`: путь, object_id, тип (ТКШ/РЩ), класс |
| `smoke_decision.py` | один запрос: проверить ключ и сеть |

Ключ: `OPENROUTER_API_KEY` в `../.env`.

## Маршрут кадра

| Маршрут | Когда | Что в системе |
|---|---|---|
| `critical` | дефект и P(последний уровень опасности) ≥ `critical_prob` | тревога в обход очереди |
| `review` | дефект или неуверенная норма | очередь диспетчера |
| `auto_ok` | норма с уверенностью ≥ `auto_ok` | подтверждено без человека |
| `not_observed` | «объекта нет» или неуверенная норма при плохой видимости | в Kafka не пишется |

Видимый дефект никогда не гасится порогом видимости: у открытого люка нет крышки, и вопрос «виден ли люк» даёт низкий балл.

## Датасет организаторов («Датасет-ДСС»)

61 фото с разметкой плюс `Фото.1.jpg` без неё. Объекты: ТКШ (телекоммуникационный климатический шкаф) и РЩ (распределительный щит). Классы: удовлетворительно, повреждение ЛКП, механическое повреждение (деформация), нарушение крепления. Тип объекта указан только в имени папки, а имена файлов в разных папках повторяются (`20211214`), поэтому разметка ищется по относительному пути.

```bash
D=../data/Датасет-ДСС          # распаковать оба zip из dataset/ в ../data
.venv/bin/python prepare_dss.py $D
.venv/bin/python worker.py $D --labels $D/labels.csv --id-col object_id --run-id final        # --kafka '' без системы
.venv/bin/python evaluate.py runs/final --labels $D/labels.csv --label-col class --kind-col kind --desc-col description --status-col status
```

Результат на всём датасете (`auto_ok` 0.6, фото 2048 px): вид повреждения верно в 91.8% случаев, все 41 дефект дошли до человека, 18% кадров закрыто без людей и все верно. Тип ТКШ/РЩ верно в 79%: на РЩ-фото рядом часто висит шкаф крупнее. Стоимость $0.014 за датасет, около 12 с при 8 потоках.

### Подбор промпта (`experiment.py`, варианты в `variants/`)

| Вариант | Точность | Мех. повреждения | Тип | Без людей при 0 пропусков |
|---|---:|---:|---:|---:|
| base: первые описания, 1280 px | 90.2% | 11/17 | 75% | 26%, запас 0.01 |
| b: «ровные панели, климатический отсек не перекошен», осмотр по частям, 2048 px | **91.8%** | **14/17** | **79%** | 25%, запас 0.01 |
| b на кропах Jev | 85.2% | 12/17 | 75% | 0%: без опоры в кадре не видно отрыва |
| b + 8 эталонных фото всех классов (`references`) | −4…−8 п.п. к b на тех же фото | хуже | ≈ | цена ×5: модель путает эталон с проверяемым фото |
| b + 2 эталона нормы (ТКШ и РЩ) | −2…−3 п.п. к b | = | +1…+4 п.п. | цена ×2 |

Эталоны сравнивались честно: сами эталонные фото исключены из подсчёта, а b пересчитан на том же подмножестве. Поддержка `references` в `taxonomy.json` осталась (пути от корня репо), но в рабочей конфигурации эталонов нет.

В b добавлены да/нет-проверки на каждый дефект (`checks`): если хоть одна ≥ `check_max`, норма не закрывается автоматически. На этом датасете они ничего не меняют, это страховка на новых фото. `auto_ok` 0.6 выбран с запасом: у дефектов, которые модель считает нормой, P(норма) не выше 0.53.

Описания правились после просмотра ошибок на этих же 61 фото. Правки общие, по смыслу разметки (МП климатического отсека — это перекос и сдвиг блока, а не только вмятины), но выборка маленькая, и честная оценка будет только на новых снимках.

## Утром, по шагам

```bash
cd ml && python3 -m venv .venv && .venv/bin/pip install -r requirements.txt   # один раз
.venv/bin/python smoke_decision.py <любое фото>          # 1. ключ и сеть на площадке
.venv/bin/python labels.py <таблица.xlsx>                # 2. какие колонки и значения в разметке
# 3. вписать их виды повреждений в taxonomy.json: classes / aliases (label = как в таблице)
.venv/bin/python worker.py <папка с фото> --labels <таблица> --file-col <колонка файла> \
    --kafka '' --limit 30 --run-id dry                   # 4. сухой прогон на 30 фото
.venv/bin/python evaluate.py runs/dry --labels <таблица> --file-col ... --label-col ...
# 5. весь датасет в систему (API запущен с MEDIA_ROOT=<папка с фото>)
.venv/bin/python worker.py <папка> --labels <таблица> --file-col ... [--id-col ... --lat-col ... --lon-col ...] --run-id final
.venv/bin/python evaluate.py runs/final --labels <таблица> --file-col ... --label-col ... [--status-col ...] [--map "метка=класс"]
```

- Ответы кэшируются в `.cache/<hash вопросов>/`. Повторный прогон и смена порогов ничего не стоят. Смена текста вопросов или классов означает новый кэш.
- Id детекций детерминированные, поэтому повторная публикация не создаёт дублей в бэкенде.
- Отчёт содержит перебор порога `auto_ok`: сколько снимаем с людей и сколько дефектов теряем. Это главный слайд.
